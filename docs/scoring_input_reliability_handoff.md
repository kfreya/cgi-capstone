## 2. Revenue fallback hierarchy

Use `apply_revenue_hierarchy(df)` — do not read `total_estimated_revenue`
directly. It returns `authoritative_revenue` and `revenue_source`
(`primary` / `fallback` / `none`):

```text
authoritative_revenue =
    total_estimated_revenue                       if not null
    else opportunity_estimated_revenue_base_cad    if not null
    else MISSING (exclude the row from load calculation)
```

`cleaned_opportunity_df` already carries a precomputed `authoritative_revenue`
column from Yixiao's cleaner; it is identical to what `apply_revenue_hierarchy`
produces. Either is fine — the helper is there so the engine does not depend
on the cleaner's internal version.

On the current data: 0 rows are unscoreable (`revenue_source == "none"`), so
every opportunity resolves a revenue figure. **Do not** add
`service_solution_estimated_revenue` to this — it double-counts.

## 3. Date and duration fallbacks

**Delivery window** (`delivery_window` rule). Start = `revenue_start_date`,
falling back to `close_date` when the primary is null; window =
`[start, start + duration_months]`. On the current data all 5,290 Won
opportunities resolve a start (5,275 via the primary, 15 via the fallback),
so no Won row is unscoreable for delivery load.

**Duration** (`missing_duration` rule). Fill null or non-positive
`project_duration_number_of_months` with 12 months. `capacity_engine.py`
already does `fillna(12)` silently — please add a counter that exposes how
many rows were filled, so the dashboard can separate "short project" from
"missing data". The 152 rows over 60 months are **not** filled and currently
inflate duration-weighted terms — flag, do not silently clip.

**`close_date < created_on`.** 379 rows on a calendar-date basis (~4%). This
is down from the Sprint 1 figure of 3,049 — that figure compared raw
timestamps (`created_on` carries a time component, `close_date` is midnight)
and was a measurement artefact. It is not a blocker for time-based features,
but `close_date - created_on` should not be used as a "time to close" metric
until CGI explains the 379 (open question in `docs/data_validation.md`).

Note: Yixiao's `close_before_created_flag` in `opportunity_cleaner.py` still
uses the un-normalized comparison and reads 3,049. Until that is fixed, prefer
`validate_date_duration_fields` / `_count_close_before_created` for the
corrected count.

## 4. Outcome taxonomy — import the helper

Do not derive Won / Lost / Open from your own string checks. Import
`classify_opportunity_outcome(df)` from `src/data_validator.py`. It returns a
Series in `{won, lost, open, duplicate, unknown}`:

- `status_reason` is canonical; `status` is the fallback for the 51
  null-reason rows. This subsumes the Sprint 1 `won_detection` rule.
- **Option B decision:** `Cancelled ...` reasons are lost-like (a real
  pipeline exit). `Duplicated` is its own bucket and is **excluded from
  win/loss/open counts** — it is a CRM data-hygiene label (zero overlap with
  the merge-level `duplicate_flag`, concentrated in 3 owners), not a sales
  outcome. This is the validation owner's recommendation pending CGI
  confirmation; if CGI says it counts as a loss, it is a one-line change in
  `DUPLICATE_REASONS` and nothing downstream of the helper moves.

On the current data: won 5,290 / lost 2,630 / duplicate 461 / open 365 /
unknown 0. Route `won` rows to delivery load and `open` rows to sales load,
per the architecture.

## 5. Owner-level findings

Your `build_director_capacity_df` (PR #29) is the owner-level director table —
that is the dashboard contract, and it is the capacity engine's scope.
`build_owner_aggregates` in `data_validator.py` is a **validation cross-check**:
an independent recomputation of the same owner-level columns, run to catch
definition divergences. Findings from that cross-check, for you to consider:

- **`inferred_delivery_commitments` differs by ~70%** — 953 from the
  cross-check vs 1,620 from `build_director_capacity_df`. Root cause: the
  engine's `delivery_active` column is not Won-gated, so non-Won opportunities
  whose date window happens to contain today are counted. `delivery_load` (the
  score) *is* Won-gated, so the module is internally inconsistent. Suggest
  gating `delivery_active` on Won.
- **`relative_load` looks mis-scaled.** The cross-check found `relative_load`
  correlates 0.999 with `quarters_of_data`. `current_load` (numerator) is a
  lifetime cumulative sum while `historical_avg_load` (denominator) is a
  per-quarter average, so the ratio is roughly "number of quarters" and all 23
  scoreable owners land at `capacity_score = 0` / Overextended. Compounding it,
  `compute_sales_load` only zeroes `sales_load` for Won, so 2,657 closed-lost
  rows (81% of total `sales_load`) still feed the numerator. The numerator
  should be a current snapshot, not a lifetime sum.
- **`baseline_reliability` should be the documented 4-tier rule**
  (`config/fallback_assumptions.yaml`: No baseline = 0 quarters / Low 1-3 /
  Medium 4-7 / High >= 8), not a 2-state boolean. The "No baseline" tier is
  now formalised in `fallback_assumptions.yaml`, `data_validation.md`, and
  `build_owner_aggregates`: it isolates the 2 owners with
  `quarters_of_data = 0` (history entirely opps1-exclusive with null
  `created_on`), whose `relative_load` is NaN and who cannot be scored at
  all. `compute_historical_baseline` should emit the same 4 tiers so those 2
  are not collapsed into an ordinary score.
- **24 owners.** The cross-check deduplicates `duplicate_flag` rows on
  `opportunity_id` before aggregating (a no-op on current data — `duplicate_flag`
  is 0 — but a cheap safeguard worth adding). `unmatched_flag` and
  `opps1_exclusive_flag` rows are kept; they are legitimate distinct
  opportunities.
- **Seven owners have fewer than 10 lifetime opportunities.** Treat their
  scores as Low reliability regardless of `quarters_of_data`.

The intra-director rule still holds: capacity labels come from
`current_load / historical_baseline_for_that_director`, never from peer
ranking.
